# NAFLD Transcriptomics Dataset Collection

This repository is a Week 1 Machine Learning internship deliverable for Survom: identify, validate, download, organize, and document **bulk** transcriptomics datasets related to Non-Alcoholic Fatty Liver Disease (NAFLD) from NCBI GEO.

It contains two things:

1. **`geo_screen`** — a reusable, auditable Python CLI that searches GEO, fetches Series/Sample metadata, runs objective technical checks, and classifies each dataset with machine-generated, traceable reasons. It is not a black-box AI selector: every verdict traces to a GEO metadata field, a named rule, or a warning that demands human review.
2. **`survom_nafld/`** — the curated collection the tool produced, plus the human decisions made on top of it.

## Purpose

The assignment explicitly warns against downloading "as many datasets as possible." The goal is a small, well-justified, reproducible collection of **bulk** RNA-seq datasets — with single-cell/single-nucleus/spatial studies, cell-line models, and other unsuitable material correctly identified and excluded, or flagged for human review where the automated evidence is ambiguous.

## Quick start

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest                                    # 62 tests, offline, no network

.venv/bin/python -m geo_screen search --query-file queries.txt --out survom_nafld
.venv/bin/python -m geo_screen screen --file survom_nafld/candidates/accessions.txt --out survom_nafld
.venv/bin/python -m geo_screen download --file survom_nafld/selected.txt --out survom_nafld
```

Screening ~200 GSEs takes a few minutes on first run (rate-limited to 3 req/s against NCBI; 10 req/s if `NCBI_API_KEY` is set in the environment) and is near-instant on every subsequent run because every fetch is cached under `.geo_cache/`. Pass `--offline` to force a run to use only what's already cached — useful for reproducing a prior run with no network at all.

## GEO search strategy

Two queries, run against `db=gds` via NCBI E-utilities, executed 2026-08-13T04:32:28Z (see `survom_nafld/candidates/search_manifest.json`):

```
NAFLD AND "Homo sapiens"[Organism] AND "expression profiling by high throughput sequencing"[DataSet Type]
(MASLD OR MASH OR NASH) AND "Homo sapiens"[Organism] AND "expression profiling by high throughput sequencing"[DataSet Type] AND liver[All Fields]
```

The first query intentionally mirrors an earlier manual search (documented in `Resources/description.md`) that returned 99 hits; this run returned 100 — the pool has grown slightly since. The second query broadens recall to the MASLD/MASH/NASH synonym family with an explicit `liver` term, in line with the assignment's own list of related terms. Together they returned **200 unique GSE accessions** (`survom_nafld/candidates/candidates.csv`, deduplicated by accession). Both queries are committed verbatim in `queries.txt`, which is what `search` actually reads — the strategy above is not paraphrased, it is what ran.

Human liver studies are prioritized, but "human only" is never hard-coded: the search itself does not filter by organism beyond `"Homo sapiens"[Organism]` in the query text, and the classifier never rejects a non-human dataset outright (see Selection policy below).

## Inclusion/exclusion criteria

Generated by `geo_screen.report.render_criteria_markdown()` directly from `rules.py` and `classify.py`, so this section cannot drift from what the code does.

### Thresholds

- Strong-candidate minimum sample count: 20
- Strong-candidate liver-source fraction: 95%

### Disease terms recognised

NAFLD, MASLD, NASH, MASH, non-alcoholic fatty liver, nonalcoholic fatty liver, metabolic dysfunction-associated stea, steatohepatitis, steatosis, fatty liver, fibrosis stage, NAS score, NAFLD activity score, Kleiner

### Single-cell/spatial signals

- **[structural]** `10x|10X Genomics|Chromium|cellranger|cell ?ranger|STARsolo|Seurat|Scanpy|alevin|Drop-?seq|Smart-?seq|single cells were|single[- ]cell (suspension|capture|controller|library)|single[- ]nucle(us|i)|nuclei (were )?isolat|snRNA|scRNA|CITE-seq|Visium|GeoMx|MERFISH|spatial transcriptom` over `Sample_extract_protocol_ch1`, `Sample_data_processing`, `Sample_library_strategy`, `Sample_title`, `Sample_source_name_ch1` — cell-resolved protocol or processing tool named in sample metadata
- **[structural]** `matrix\.mtx|barcodes\.tsv|features\.tsv|genes\.tsv|filtered_feature_bc_matrix|\.h5ad|\.loom|tissue_positions` over `Sample_supplementary_file`, `Series_supplementary_file` — single-cell/spatial file format in a supplementary filename
- **[textual]** `single[- ]cell|single[- ]nucle|spatial transcriptom` over `Series_summary`, `Series_overall_design`, `Series_title` — series free text mentions single-cell/spatial work; bulk papers routinely discuss it in background without using it themselves

### Non-tissue / cell-line signals

- **[structural]** `HepG2|Huh-?7|HuH-?7|Hep3B|HepaRG|\bL02\b|LX-2|AML12|THP-1|EA\.?hy926|cell line|organoid|spheroid|iPSC|hiPSC|pluripotent stem cell|in vitro|cultured (primary )?hepatocyte` over `Sample_source_name_ch1`, `Sample_title`, `Sample_characteristics_ch1` — sample metadata itself names a cell line, culture, or in vitro model
- **[textual]** same pattern over `Series_title`, `Series_summary`, `Series_overall_design` — series prose mentions a cell/culture term; sample metadata does not corroborate

**Sample-level evidence outranks series prose everywhere.** A structural hit forces REJECT (single-cell) or WARN→MANUAL_REVIEW (cell line); a textual-only hit is downgraded to WARN or INFO respectively. Abstracts discuss other people's methods and the paper's own discussion section; sample records describe what was actually sequenced. See `GSE213621` below for a real case this distinction resolves correctly.

### Classification precedence (first match wins)

1. `single_cell_or_spatial` = FAIL → **REJECT** — cell-resolved assay; not bulk transcriptomics
2. `disease_relevance` = FAIL → **REJECT** — no NAFLD-spectrum term in series or sample metadata
3. `library_strategy` = FAIL → **REJECT** — no expression-profiling samples
4. `expression_data_availability` = FAIL → **REJECT** — no downloadable expression data
5. any check = WARN → **MANUAL_REVIEW**
6. organism == *Homo sapiens* and all of `source_tissue`, `library_strategy`, `disease_relevance`, `sample_count`, `expression_data_availability` = PASS → **STRONG_CANDIDATE**
7. otherwise → **CANDIDATE**, with unmet conditions listed

## Selection policy (our decision, not a biological rule)

The classifier never treats non-human organism as a REJECT — Survom's brief explicitly notes GEO holds NAFLD-relevant studies from humans and other organisms, and a mouse NAFLD model is real, valid biology, just not equivalent to human NAFLD. A non-human dataset is screened, scored, and reported exactly like any other candidate; it is only ever capped at `CANDIDATE`, with the reason `organism != Homo sapiens — model system, not equivalent to human NAFLD` in `unmet_strong`.

Keeping non-human datasets out of the **downloaded** collection below is a curation decision for this assessment, not a claim that they are invalid: the brief centers on human disease, and every human `STRONG_CANDIDATE` dataset already available made non-human inclusion unnecessary here. In the 200-dataset pool screened, no candidate reached `STRONG_CANDIDATE` or `CANDIDATE` on an exclusively non-human basis in a way that would have changed this decision; several human/mouse **mixed**-organism series (e.g. `GSE267145`, 448 human + 60 mouse samples) landed in `MANUAL_REVIEW` instead, and are discussed below.

## Screening workflow

1. `search` queries `esearch`/`esummary` (db=gds), writes `candidates/candidates.csv`, `candidates/accessions.txt`, `candidates/search_manifest.json`.
2. `screen` fetches each GSE's `*_family.soft.gz` (one request — every GSM's metadata included) plus two small FTP directory listings (`suppl/`, `matrix/`), runs the 14 checks, classifies, and writes the four mandated files (`series_metadata.json`, `sample_metadata.csv`, `validation_report.md`, `source_manifest.json`) under `datasets/<GSE>/`, plus the aggregate `reports/summary.csv` and `reports/screening_report.md`.
3. A human reads `reports/screening_report.md`, resolves `MANUAL_REVIEW` entries that matter, and writes `selected.txt`.
4. `download` fetches the tiered, human-selected files only — screening itself never downloads bulk data.

**Result: 200 candidates screened → 11 STRONG_CANDIDATE, 8 CANDIDATE, 131 MANUAL_REVIEW, 50 REJECT.** All 200 succeeded (no fetch failures). Every candidate has a full validation report under `survom_nafld/datasets/<GSE>/`.

`REJECT` breakdown by the check that fired: `single_cell_or_spatial` (45 — the dominant rejection reason, exactly the failure mode the assignment calls out by name), `library_strategy` (2 — non-expression assays like Bisulfite-Seq-only or ChIP-seq-only series), `disease_relevance` (2), `expression_data_availability` (1).

## Manual-review resolutions

131 datasets landed in `MANUAL_REVIEW`. Given the volume, the ones examined in depth are the ones large enough to plausibly change the collection, plus a scan for any large dataset flagged only because of a metadata-mapping gap. This is not exhaustive — `reports/screening_report.md` lists every one with its triggering reason for anyone continuing this work.

**`GSE213621` (368 samples) — resolved and included.** Flagged on two checks:

- `metadata_completeness`: WARN, "no disease/diagnosis/group/stage-type canonical field reported anywhere." Investigation: the series *does* report fibrosis staging per sample, under the raw characteristic key `fibrotic stage` (e.g. `fibrotic stage: F2`) — an adjective form the tool's synonym table didn't recognize (it only had `fibrosis stage`). Fixed by adding `fibrotic stage` and `fibrosisscore` as `fibrosis_stage` synonyms, and `patient diagnosis` as a `diagnosis` synonym, in `rules.py`. Re-screening the full 200-candidate pool after the fix raised `STRONG_CANDIDATE` from 9 to 11 (`GSE150026` and `GSE272035` also newly qualified). `GSE213621` itself still didn't reach `STRONG_CANDIDATE` outright — see the next point — so its inclusion here is a human decision on top of the corrected metadata, not an automatic promotion.
- `disease_relevance`: WARN, "found only in series-level text, not corroborated by sample metadata." This is correct as designed: individual GSM records say `liver cells` / `fibrotic stage: F2`, never spelling out NAFLD by name, while the series title ("...Nonalcoholic Fatty Liver Disease") does. Per the sample-level-outranks-series-prose rule, that is a legitimate WARN, not a bug — it is exactly the situation `MANUAL_REVIEW` exists for. Manually confirmed: `library_strategy` is RNA-Seq for all 368 samples with no structural single-cell signal in any sample record (the accompanying `single_cell_or_spatial` WARN is also textual-only, same resolution). Included given its size and genuine fibrosis staging.

**Large mixed-organism and mixed-assay series — left in `MANUAL_REVIEW`, not resolved.** `GSE267145` (508: 448 human + 60 mouse), `GSE246223`/`GSE246221` (human+mouse), and `GSE105127` (114: 57 Bisulfite-Seq + 57 RNA-Seq) all contain a genuine bulk-RNA-seq human subset worth extracting, but `geo_screen` currently classifies a GSE as one unit — it has no notion of "screen only the human samples in this series." Resolving these properly means adding sample-level subsetting to the tool, which is out of scope for this pass; they are flagged here as the most promising direction for a follow-up iteration rather than silently dropped.

**Everything else in `MANUAL_REVIEW`** was left for review by whoever picks this up next, prioritized by `n_samples` in `reports/screening_report.md`. The 7 selected datasets already meet the collection's goals; there was no need to force additional MANUAL_REVIEW promotions once GSE213621 was resolved.

**Known limitation — disease-term matching does not distinguish presence from absence.** `disease_relevance` matches `DISEASE_TERMS` as a substring against raw characteristic strings, so a characteristic like `nash: no` counts as a "hit" on the literal word "nash" even though the value says the sample does *not* have NASH (this is why `GSE239422`, all "Obese", still shows `disease_relevance` = PASS for every sample). It does not change any classification outcome here — a genuinely NAFLD-relevant series still needs *some* real disease-spectrum content to reach PASS, and manual review of the affected checks table always shows the underlying raw value — but it means "PASS" should be read as "a disease term appears in this field," not "this sample has the disease." Worth fixing (e.g. skipping `no`/`none`/`negative`/`normal` immediately after the matched term) in any follow-up work on this tool.

## Download process and caveats

`download` is a separate, explicit step from `screen` — screening never pulls large files. For each selected GSE:

1. **Tier 1**: series-level supplementary files matching `counts|matrix|tpm|fpkm|rpkm|expression|cpm|.csv|.tsv|.txt` (excluding NCBI's auto-generated `filelist.txt` directory index, which matched this pattern and was excluded after being caught downloading nothing but a file listing for `GSE135251`) go to `expression/`.
2. **Tier 1b**: phenotype/clinical/metadata files and the series matrix go to `metadata/`.
3. **Tier 2** (only if Tier 1 found nothing): the series `_RAW.tar` goes to `archives/` as downloaded — a `_RAW.tar` is GEO's archive of per-sample submitted files, **not raw FASTQ** — and `extract_archive()` pulls only the processed count files it contains into `expression/` (`GSE135251`: 216 per-sample `.counts.txt.gz` files this way). Extraction uses Python 3.12's hardened `filter="data"`, which rejects path traversal, absolute paths, and symlinks.
4. SRA/FASTQ is **never** downloaded — links are recorded in `download_manifest.json` and the `raw_sra_availability` check only.
5. Anything over `--max-file-size` (default 500 MB) is skipped with the reason logged.

**Security note — filenames from network listings are untrusted input.** Every filename `download` writes to disk comes from parsing either an FTP directory listing (HTML from the network) or a `!Sample_supplementary_file_N` SOFT field (free text from the network). A path-traversal review of this code found that those names were joined onto a local directory path (`dest_dir / name`) without validation — `Path.__truediv__` does not sanitize `..` components, and for an absolute-looking name it silently discards the destination directory entirely. `download.py` now rejects any name containing a path separator or an exact `..`/`.` component, both where a `Plan` is built (`plan_downloads`, skip-with-reason, same pattern as an oversized file) and again where a name is actually turned into a filesystem path (`_fetch_named`), so the check holds even if a `Plan` is constructed directly. This is separate from, and in addition to, the tar-extraction hardening in point 3 above — that one protects against a malicious archive's internal member names; this one protects against a malicious or malformed directory listing.

**Caveat confirmed in this run:** `series_matrix` presence does not mean expression data is present. Every selected dataset's samples are `Sample_type = SRA` with `Sample_data_row_count = 0`, so their series matrix files are metadata-only — the `series_matrix` check reports `present, metadata-only` for exactly this reason, and `expression_data_availability` is evaluated independently from supplementary-file evidence.

**Reliability note:** large-file downloads over the FTP mirror occasionally hit `ChunkedEncodingError` (`IncompleteRead`) mid-transfer — a connection reset *after* a 200 response, which `requests`' status-code-based `Retry` adapter does not cover. `GeoClient._http_get` retries this specific error up to 3 times with backoff; it was triggered and recovered automatically while downloading this collection.

All 7 downloads verified: every file's sha256 in `download_manifest.json` matches the file on disk (checked with a one-off `hashlib.sha256` pass over every downloaded file against its manifest entry).

## Reproducibility

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/python -m pytest                       # 62 tests, all offline, ~2s

# Optional: set NCBI_API_KEY in the environment for a 10 req/s rate limit instead of 3 req/s.

.venv/bin/python -m geo_screen search --query-file queries.txt --out survom_nafld
.venv/bin/python -m geo_screen screen --file survom_nafld/candidates/accessions.txt --out survom_nafld
.venv/bin/python -m geo_screen download --file survom_nafld/selected.txt --out survom_nafld
```

First `screen` run: a few minutes (200 GSEs x 3 requests, rate-limited). Every later run against the same `.geo_cache/` is seconds, and `--offline` reproduces it with zero network calls — this is how the rule fix above was verified against all 200 candidates in ~7 seconds instead of re-fetching everything.

```bash
.venv/bin/python -m geo_screen GSE135251 --out /tmp/run1
.venv/bin/python -m geo_screen GSE135251 --out /tmp/run2 --offline
diff -rq /tmp/run1/datasets /tmp/run2/datasets
```

Verified: the only file that differs is `source_manifest.json`, and only in fields that are *supposed* to change between invocations — the recorded `argv` (`--out /tmp/run2 --offline` vs `--out /tmp/run1`) and the cache provenance (`from_cache: true` vs `false`, and the one-second-apart `retrieved_at`). `series_metadata.json`, `sample_metadata.csv`, and `validation_report.md` are byte-identical.

## Architecture notes

`geo_screen` fetches exactly one `*_family.soft.gz` per GSE (every GSM's metadata is in that one file — no per-sample scraping) plus two small FTP directory listings. Runtime dependency is `requests` only; everything else (CSV, JSON parsing, characteristics normalization) is the standard library. Fourteen checks each produce a `PASS`/`WARN`/`FAIL`/`INFO` status with an `observed` string and, where relevant, `Evidence` records naming the exact SOFT field and matched text — every number in a report traces to a specific field in a specific GEO record, never to a hand-typed figure. Classification is a pure function over the 14 check results, evaluated by fixed precedence (above); it has no access to the network and cannot be influenced by anything except the check outcomes.
